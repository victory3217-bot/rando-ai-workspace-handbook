## 1. Learning Objectives

When you finish this chapter, you will be able to do the following.

- Explain how a work procedure relates to an AI Workflow.
- Divide a task into *input → processing → verification → output* and draw it as a flowchart.
- Decide the decision points (human approval points) where a person must step in.
- Write the handling of failures and exceptions in an exception handling table.
- Create a standard operating procedure and a run checklist for a repeating task.
- Know how to keep a run log and find improvements.
- Explain the difference between a simple workflow and a harness.
- Explain the differences among human-led AI use, a pre-designed AI Workflow, and an Agentic Workflow, and choose a suitable approach by looking at the risk and repeatability of the task.

## 2. Core Concepts

**Terms used in this chapter**
- **Work procedure**: the order in which a task is done.
- **AI Workflow**: a design of the steps and procedure of a task. It can include which steps a person does and which steps AI does, the input and output of each step, checks, and exception handling (this book's working definition).
- **Decision point (human approval point)**: a place where a person must judge or approve directly.
- **Exception**: a situation in which things do not go according to the set procedure.
- **Standard operating procedure**: a procedure written down so that anyone does the task in the same order.
- **Run log**: a record, kept each time you run the task, of the date, input, result, and problems.
- **Harness**: an execution system that supports and controls AI in carrying out a specific task (this book's working definition, not an industry-standard definition).
- **AI Agent**: an AI-based system that, within a given goal and an allowed permission boundary, assesses the situation, chooses the actions needed, and uses tools to carry the work forward (CH01 section 2-5, this book's working definition).
- **Agentic Workflow**: a way of working in which an AI Agent decides the next action or tool use according to the situation, within a set goal, tools, permissions, and limits (this book's working definition).
- **Permission Boundary**: the limits of the materials and tools an agent can read, write, and send.
- **Human-in-the-loop**: placing a step in which a person judges or approves inside the flow.

### 2-1. How a work procedure relates to a workflow

A work procedure is an *order*. An AI Workflow adds to that order *who (person or AI) does it, what they receive, what they produce, how it is checked, and what to do if it fails*. If the work instructions in CH10 are *the rules the AI follows*, the workflow in CH11 is *the design that places those rules inside the flow of the work*.

> **Author's interpretation** The three concepts in this book (AI Workspace, AI Workflow, AI Harness) are not mutually exclusive categories. They can be connected or contain one another. A workflow can also include verification and exception handling. This distinction is this book's working definition, and I do not claim it is an industry standard.

### 2-2. Input → processing → verification → output

```text
[Input]  →  [Processing]  →  [Verification]  →  [Output]
 What comes in   Who does what   How do we check it is right   What comes out, and who gets it
```

An example flowchart for candidate A:

```text
[Input] Meeting notes (masked, CH03 B)
   ↓
[Person] 1. Check the notes' tier and masking  ──(personal information found)→ [Stop: do not process; notify the person in charge]
   ↓ (no problem)
[AI]   2. Draft the meeting minutes following the work instructions (v02)
   ↓
[Person] 3. Compare with the original using the fact-check table, recalculate numbers        ← Verification
   ↓
◆ Approval point: Has the manager checked the content? ──(No)→ [Fix, then back to 3]
   ↓ (Yes)
[Person] 4. Save the final version (03_Final), record the approval
   ↓
[Output] Share with the team (a person sends it directly)
```

**How to read it:** A box `[ ]` is a step, `◆` is a decision point, an arrow is movement, and the words in parentheses are conditions. You can also draw it by hand on paper.

### 2-3. Decision points where a person must step in

> **Author's interpretation** Make it a human approval point if any of the following applies (the author's suggestion).
> - **Going outside:** sharing, sending, posting, submitting
> - **Hard to undo:** deleting, overwriting, decisions involving money
> - **Needs judgment and responsibility:** who takes on what, whether something is true
> - **Before entering material into AI:** checking the tier (CH03), the masking status
> - **When the AI is unsure or shows signs of breaking a rule**
>
> This book's principle is *not to hand these points over* to AI. We treat AI not as something that acts on its own, but as something that follows the instructions and reports when it does not know. Even when you use an approach in which the AI chooses its own actions, as an agent does, these points remain human approval points (section 2-8).

### 2-4. Task failure and exception handling

| Situation | What to do |
|---|---|
| The input material is empty or in a different format | Do not start; ask for the input to be completed |
| Personal information or a password appears in the material | Stop, notify the person in charge, and delete the conversation (CH03 section 7) |
| The AI produced a result that breaks a rule in the work instructions | Discard the result or rewrite it, and note the broken rule in the improvements (CH10) |
| A number or quotation differs from the original | Correct it using the fact-check table. If you cannot correct it, leave it as "Needs confirmation" |
| The AI service is down or you hit a limit | A person does it directly with the work instructions, or postpones it to the next day (if there is a deadline, notify the person in charge) |
| There is no approver, or approval is delayed | Do not share; wait. If the deadline is urgent, check with a superior |

### 2-5. Standard operating procedure for a repeating task

A standard operating procedure (SOP) is the flowchart turned into *sentences in numbered order*. For each step, write in one line *who, what they receive, what they do, and what they leave behind*.

```text
Step | Owner (person/AI) | Input | What is done | Result / what is left behind | Next condition
1 | Person | Masked notes | Check tier and masking | Check mark | No problem → 2 / Problem → stop
2 | AI | Notes, work instructions | Write the draft | _AI_draft file | → 3
3 | Person | Draft, notes | Fact-check table, recalculate numbers | Fact-check table | Errors found → fix / None → 4
4 | Person (approver) | Corrected version | Final check and approval | Approval record | Approved → 5
5 | Person | Final version | Save to 03_Final, then share | Run log | End
```

### 2-6. Run log and improvement

Keep a short record each time you run the task. Improvement is *finding problems that repeat in the log*.

```text
Run log
Run date | Work instructions version | Input (name) | Time needed (measured by me) | Problems / exceptions | Approver | Improvement idea
```

> **Author's interpretation** Whether time went down or errors went down is *not a fact this book has confirmed; it is something you confirm from your own records*. Until records build up, do not say it works. Make improvements one at a time (CH10), and I recommend skimming the log about once a month (the author's suggestion, not tested).

### 2-7. Differences between a simple workflow and a harness

| | Simple workflow (this chapter) | Harness |
|---|---|---|
| Focus | Design of steps, owners, approvals, and exceptions | An execution system that supports and controls how AI carries out the task (rules, tools, input and output conditions, verification criteria, exception handling, and so on) |
| How it is made | Paper, documents, text diagrams | Beyond documents, a setup that makes the AI apply the rules every time may be added |
| In this book | Required in CH11 | Covered in the optional, advanced course |
| Relationship | A harness can use the steps of a workflow | A workflow can be placed inside a harness |

The document set that combines the work instructions in CH10 and the flowchart in this chapter can be seen as a *starting point* that moves closer to a harness (Author's interpretation). However, a setup that makes the AI apply those rules automatically every time is not required in this book. For the structure of the instruction documents of a public harness, see the case in CH10.

### 2-8. Three Ways of Handing the Same Task Over: Human-Led, Designed Workflow, Agentic Workflow

Even for the same task, the ways of handing it to AI fall into roughly three. The definitions of the chatbot, workflow, agent, and harness were given in CH01 section 2-5, so here we look at the difference in *how the work is actually carried out*.

> **Author's interpretation** The distinction below is this book's distinction for teaching.

| | Way 1. Human-led AI use | Way 2. Pre-designed AI Workflow | Way 3. Agentic Workflow |
|---|---|---|---|
| Who decides the next step | A person, as it comes | Steps and branch conditions set in advance | The AI Agent, according to the situation, within a set goal, tools, permissions, and limits |
| What the AI does | The work a person asks for (writing, summarizing, analyzing, and so on) | Analysis, generation, classification, and so on in some steps | Chooses the next action and tool use and carries the work forward |
| What the person does | Decides the steps, makes the request, and verifies the result | Designs the flow and checks at the approval points | Sets the goal, the allowed materials and tools, the permission boundary and limits, then approves, verifies the result, and is responsible |
| Predictability of the path | Depends on the person | High (a fixed path) | May be lower, because it can vary with the situation |
| In this book | The way of working in the CH09 exercises | The required exercises of CH11 | Explained as a concept only. There is no exercise that builds or runs it |

The three ways are not *maturity stages* you climb in order, and the later way is not always better. Which way fits depends on the risk of the task, how often it repeats, how clear the rules are, the cost, and whether the result can be verified.

> **Official documentation check — AI Agent descriptions (Anthropic, Microsoft), checked on 2026-10-26**
>
> - Anthropic distinguishes a workflow as a system in which LLMs and tools are orchestrated through predefined code paths from an agent as a system in which the LLM directs its own process and tool use. Because autonomy means higher costs and the potential for compounding errors, it recommends starting with the simplest solution possible and adding complexity only when needed. `[S16]`
> - Microsoft Learn's security guidance says agents can produce real-world effects through tool calls and data access with limited human intervention, and recommends letting users set the boundaries of what agents can access and do, applying least privilege, requiring approval for high-risk or irreversible actions, and providing a way to stop immediately along with execution logs. `[S19]`
> - Microsoft's Entra documentation says an agent can act with or without human intervention, and that each tool an agent uses needs careful consideration of security, permissions, and error handling. `[S18]`

> **Author's interpretation** Criteria for choosing a way (the author's suggestion, not tested)

| Criterion | When Way 1 or 2 fits | When Way 3 can be considered |
|---|---|---|
| Risk of the task | Sending outside, deleting, money, or personal information is involved → human-led, or a designed flow with approval points | Only for tasks that can be undone and have small impact (reading, organizing, marking) |
| Repetition | It repeats in the same order every time → a designed Workflow | The steps are not fixed in advance and vary with the situation |
| Clarity of rules | The rules are clear → write them as the Workflow's branch conditions | The rules are hard to write out fully, and you must look through materials to judge |
| Cost | The number of calls and the time are fixed, so it is easy to predict | Keep in mind that steps can multiply and cost and time can grow `[S16]` |
| Verifiability | The result can be checked with the fact-check table | Only when a record remains of what was read and made, so a person can verify it `[S19]` |

> **Author's interpretation** Basic principles when using the agent approach (this book's operating principles for teaching)
>
> - Write down *in words* the goal, the allowed materials, the tools it may use, and what it must not do (an extension of the CH10 work instructions).
> - Start with the narrowest permission boundary. Start by allowing reading only; do not allow editing files, sharing, sending outside, or deleting by default, and keep them as human approval points (section 2-3).
> - The information tiers (CH03) and your organization's rules come first.
> - After a run, check what it read and what it made, and verify the result with the CH12 procedure.
> - Check in the product's official documentation which tools and permission settings it supports. This book has not confirmed any particular product's automatic execution, file modification, or external service operation features.

## 3. Workplace Application

Gasang Han at the fictional company Example Trading Co. had been organizing meeting minutes every week, and drew a workflow so that "anyone does it in the same order." (All fictional)

| What was found | Action taken |
|---|---|
| A draft was once shared with the team right after it was made | Created an approval point and decided "sharing is done directly by a person after approval" |
| Attendees' contact details once came mixed into the notes | Added a tier check and a stop condition to Step 1 |
| A colleague had to cover during vacation | Made it possible to do the task using only the flowchart, work instructions, and run checklist |
| With no run log, it was hard to find what to improve | Made a run log template and decided to skim it after a month |

The effects (such as how much time was saved) are not something this book has confirmed; they are fictional expectations. This chapter does not include a new harness case.

**The same task handed over in three ways** *(a fictional example for explaining the concepts)*

The task: "Make a follow-up action list from the meeting notes and check for missing information." (Gasang Han, all fictional)

- **Way 1. Human-led:** Paste the masked notes into an AI service and ask, "Organize the follow-up actions as a table." Gasang Han looks at the result, asks again, "Is anything missing, such as an owner or a deadline?", and checks it directly against the notes and corrects it. What to do next is decided by Gasang Han as it comes.
- **Way 2. Designed Workflow:** Proceed along the flowchart in section 2-2. (1) A person checks the tier and masking → (2) the AI drafts the list following the work instructions (v02) → (3) a person compares it with the fact-check table and marks missing items "Needs confirmation" → (4) the manager approves → (5) save, then share. The steps in which the AI works are fixed.
- **Way 3. Agentic Workflow:** Gasang Han sets the goal ("make the follow-up action list and mark items missing an owner or a deadline 'Needs confirmation'"), the materials it may read (the masked notes and the folder of past minutes, *read only*), what it must not do (edit files, share, send outside, delete), and the approval point (checking the final list). The agent then chooses for itself which materials to look at in what order and produces a draft list and the items needing confirmation. Which tools and permission settings are possible differs by product and settings, and this book has not confirmed them.

In all three ways, a person does the final check and the sharing. In Way 3, checking the record of *what the agent read and made* is added.

## 5. Step-by-Step Practice

**Exercise name: Designing the workflow for candidate task A**

- **Starting state:** You have candidate task A and its purpose, work instructions v02, the fact-check table, and the approval record (if not, use the fictional example).
- **Finished state:** You have ① a work flowchart, ② a step-by-step run procedure, ③ human approval points, ④ an exception handling table, and ⑤ a run checklist. You have one line of trial run log.

### Exercise 1. Draw the work flowchart

Take the run steps from the CH10 work instructions and draw them in the shape shown in section 2-2. You can draw it on paper or write it as a text diagram in a notepad. Include input, processing (person/AI), verification, and output, and mark decision points with `◆`.

```text

Candidate task A / purpose (CH01):
[Input] →
```

### Exercise 2. Write the step-by-step run procedure

Move the flowchart into the table in section 2-5. For each step, write the owner (person/AI), input, what is done, what is left behind, and the next condition. Write storage locations using the folder names from CH04 and the knowledge document numbers from CH08.

```text
[2] Step-by-step run procedure
Step | Owner (person/AI) | Input | What is done | Result / what is left behind (storage location) | Next condition
1 |
2 |
...
```

### Exercise 3. Decide the human approval points

Using the criteria in section 2-3, pick the approval points from the flowchart and write them in a table.

```text
[3] Human approval points
Point (after which step) | Why a person must decide (criterion) | Who approves (role) | What is checked | Where the approval record is kept
...
What is not handed over to AI:
```

### Exercise 4. Make the exception handling table

Based on the CH09 error types, the CH10 exception handling, and section 2-4, write at least six exceptions that could occur in candidate A.

```text
[4] Exception handling table
Situation | At which step | What to do | Who to notify | What to put in the record
...
```

### Exercise 5. Make the run checklist

Make the items a person checks in one run, divided into *before starting, during the run, and after finishing*. It must fit on one page.

```text
[5] Run checklist
Before starting: □ Checked the tier of the input material □ Checked the work instructions version □ ...
During the run: □ Compared the AI result using the fact-check table □ ...
After finishing: □ Recorded the approval □ Saved the final version to 03_Final □ Wrote the run log □ ...
```

### Exercise 6. One trial run and the run log (optional. Can be substituted without an AI service)

Follow the workflow once from start to finish using the fictional notes in CH09 section 5. **Path A:** Run the step that uses an AI service (Step 2) in a Project (fictional data only). **Path B:** A person writes the AI step directly following the work instructions, or uses the fictional AI draft from CH09. While you follow along, mark the places where you get stuck and leave one line in the run log.

```text
[6] Trial run log
Run date | Work instructions version | Method (AI service used / person substitute) | Input (name) | Time needed (measured by me) | Where I got stuck / exceptions | What to fix in the flowchart or procedure
```

## 6. Verify the Result

You are done if all of the following are true.

1. The flowchart has input, processing, verification, and output, and shows at least one decision point (`◆`) and a stop condition.
2. Every step of the run procedure has an owner (person/AI), input, what is done, what is left behind, and a next condition.
3. Every approval point has a reason (criterion), an approver role, and what to check. The steps that go outside (sharing, sending) always have an approval point.
4. The exception handling table has six or more exceptions, each with what to do and who to notify.
5. The run checklist is divided into before starting, during the run, and after finishing, and fits on one page.
6. You checked for yourself whether someone else could do the task using only the flowchart, work instructions, and checklist.
7. You did not assert an effect (such as time saved) without records. You did not write real personal information or confidential information anywhere.

> **Author's interpretation** A fictional example of an approval point and an exception (the author's example, not the correct answer)
>
> ```text
> Approval point | After Step 3 | Before going outside / judgment and responsibility | Manager | Fact-check table complete, numbers recalculated, unconfirmed items marked "Needs confirmation" | Approval record in 03_Final
> Exception | Contact details in the notes | Step 1 | Stop, do not process | Person in charge | If there is a conversation, delete it and note it in the run log
> ```

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| The flowchart is too complicated | Too much was put in at once | Split the task in two, or send detailed steps to the work instructions. Keep only the big steps in the flowchart |
| There are too many approval points | An approval is placed on every step | Place them only on things that go outside, things that are hard to undo, and things that need judgment and responsibility |
| There is no approval point at all | You tried to leave everything to AI | At minimum, place a human approval point before sharing or sending |
| It is hard to think of exceptions | You have never actually run it | Do the trial run (Exercise 6) and add the places where you got stuck as exceptions. Refer to the CH09 error types |
| The work instructions and flowchart differ | Only one of them was changed | Bring both to the same version and note it in the change record (CH10) |
| The trial run takes longer than expected | It is your first time and you are not used to it | This time is your own measured record, so write it as it is. Do not assert an effect |
| You worry you have to build a harness | It is not required in this book | The document set in this chapter is enough. Building one is covered in the optional, advanced course |
