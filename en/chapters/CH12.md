## 1. Learning Objectives

When you finish this chapter, you will be able to do the following.

- Explain why AI results must be verified every time.
- Compare the source text and the result in *both directions*, and verify numbers, dates, people, and sources item by item.
- Tell apart and find omissions, format errors, and content generated without evidence.
- Decide, based on the severity and type of an error, whether to *re-run, fix it yourself, or check with a person*.
- Record errors and carry them into improvements to the work instructions (CH10) and the workflow (CH11).
- Create a verification checklist and a human final confirmation record for the candidate A output.

## 2. Core Concepts

**Terms used in this chapter**
- **Verification checklist**: A list of the items to check in a result, written in advance. It makes anyone check in the same order.
- **Two-way comparison**: Comparing in two directions: from the result to the source text (finding fabrications) and from the source text to the result (finding what is missing).
- **Severity**: How big a problem an error is. This book uses high, medium, and low.
- **Re-run**: Asking the AI again with the same work instructions and material.
- **Error log**: A record of the type, cause, and action for each error you find.

### 2-1. Why AI results must be verified

- AI can make up content that is not in the source text, get numbers wrong, or leave things out (the error types in CH09). This book does not say that AI is never wrong.
- Even with work instructions, AI can break them (CH10). That is why you need *a procedure to notice whether it broke them*.
- The moment you share or submit a result, the responsibility is the person's (CH09, this book's position).
- What matters in verification is not *doing it well once* but *doing it with the same procedure every time*. To avoid skipping it when you are tired or in a hurry, you need a checklist.

> **Author's interpretation** If your answer to CH01 diagnostic Q4 ("I have written down the criteria for checking AI results") was "No," this chapter is the answer. When you finish this chapter, you will have a *document* (a checklist and a decision table) with which you can answer "Yes" to Q4. However, this book has not verified that this raises the accuracy of results.

### 2-2. Telling apart fact, inference, assumption, and unconfirmed information (CH09 review)

You turn the four distinctions you learned in CH09 into a *marking rule*. Write **only facts** in the final output, mark inferences and assumptions so they stand out, and write unconfirmed items as "Needs confirmation." When you verify, first ask of each sentence which of the four it falls under. For detailed definitions and examples, see CH09 again.

### 2-3. Comparing the source material and the output: in both directions

| Direction | What you look for | Method |
|---|---|---|
| Result → source text | Fabrications, distortions | For each sentence in the result, find its evidence in the source text. Mark any you cannot find |
| Source text → result | Omissions | Find each item in the source text (agenda item, decision, owner, deadline, undecided matter) in the result, one by one |

**You must compare in both directions.** If you only go from result to source text, you cannot find *what is missing*; if you only go from source text to result, you cannot find *what was slipped in*.

### 2-4. Verifying numbers, dates, people, and sources

| Item | How to check | Common errors |
|---|---|---|
| Numbers | Compare with the source text character by character, recalculate totals and ratios yourself, check units | Digit, unit, and total errors |
| Dates and deadlines | Is it the wording of the source text as is? Did it turn "by next week" into a weekday or a date? | Adding a weekday or date that does not exist, off by one day |
| People | Do the name and role (owner, reviewer) match the pairing in the source text? | Owner and reviewer swapped, another person's name |
| Sources | Does the document number the result cites (for example K01) actually exist in the index (CH08), and is its content right? | A document number that does not exist, misdescribing a document that does exist |

### 2-5. Omissions and format errors in results

- **Omission:** An agenda item, undecided matter, or "Needs confirmation" mark that was in the source text is missing.
- **Format error:** It differs from section 4 (output format) of the CH10 work instructions. It is written in paragraphs instead of a table, a required column is missing, or there is no list of items needing confirmation.

A format error is recorded even when the content is right, because it is a *rule violation*. If the same format error keeps recurring, it is a sign that the output format sentence in the work instructions is vague.

### 2-6. When AI generates content without evidence

1. **Do not use that sentence.** Delete it or change it to "Needs confirmation."
2. **Find the cause:** Was the input material vague? Was the prohibition rule missing or weak in the work instructions? Was an out-of-scope question mixed into the request?
3. **Prevent a recurrence:** Add the case to the prohibitions, exception handling, and verification criteria of the work instructions (CH10), and put it into the test cases.
4. **Record it:** Log it in the error log with the type "fabrication."

### 2-7. Criteria for deciding whether to re-run, fix, or check with a person

> **Author's interpretation** The following are decision criteria the author made for teaching. They are not a set standard, and your organization's rules come first.
>
> **Severity:** *High* = an error in a core item such as a decision, owner, deadline, or number, or an error that could cause harm if it goes outside / *Medium* = an error that is not core but changes the meaning, or an omission / *Low* = wording, format, and the like.
>
> | Situation | Action |
> |---|---|
> | No errors | Go on to the human final confirmation (section 2-8) |
> | A few low-severity errors | A person fixes them directly |
> | The same error is likely to repeat because of a problem in the instructions or the input | Fix the instructions or the input, then **re-run**. Record what you fixed |
> | There is a high-severity error, or there are several fabrications | Discard the result, find the cause, fix it, and re-run |
> | The same high-severity error repeats even after re-running (this book's recommendation: up to 2 times) | A person writes that part directly. Put it on the work instructions improvement list |
> | Judgment is needed, a rule is vague, or a tier (CH03) problem is suspected | Check with the owner or approver. Do not share before checking |
>
> "Up to 2 times" is a recommendation for learning and has not been tested.

### 2-8. Error log and ways to improve

Record errors *one line each time you find one*. As the records accumulate, they show which types occur often, which decides where to improve (this connects to the run log in CH11).

```text
Date | Work instructions version | Error type (fabrication/distortion/omission/calculation/format/overconfidence/source) | Severity | Where (sentence) | Cause (estimated) | Action (fixed directly/re-run/asked for confirmation) | Recurrence prevention (improvement list number in the work instructions)
```

About once a month, skim the records, count *the number per type*, and put the most frequent type on the CH10 improvement list (the author's suggestion; not tested).

## 3. Workplace Application

At the fictional company Example Trading Co., Gasang Han made a draft of meeting minutes every week and used a verification checklist. (All fictional)

| Week | What was found | Action |
|---|---|---|
| Week 1 | The AI made up a weekday for a deadline (high) | Discarded the draft; added "do not make up weekdays" to the prohibitions in the work instructions, then re-ran |
| Week 2 | The output came as paragraphs, not a table (low) | Fixed it into a table directly. Made the output format sentence more specific |
| Week 3 | In the same month, it cited a document that has no "source document number" (medium) | Checked against the index and deleted it; added "only document numbers that are in the index" to the work instructions |

Gasang Han skimmed the error log a month later, counted *the number per type*, and decided to improve the most frequent one first. Whether the effect (fewer errors) really occurred is not something this book has confirmed; it is something to confirm from your records. This chapter does not use a harness case.

## 6. Verify the Result

You are done if all of the following are true.

1. The verification checklist has the items for comparison (both directions), numbers, dates, people, sources, format, prohibitions, and after finishing, and each item states what it is compared against.
2. The error log has 6 or more errors, each with a type, severity, evidence in the source text, and what was fixed, and it records the omission found by the source text → result comparison.
3. Every error in the decision table has an action, and each error where you chose re-run has a place to fix in the work instructions or input.
4. The final confirmation record has the items checked, the remaining items needing confirmation, the approver role, and the final judgment.
5. The type of run (`[Live AI run]`/`[Simulated run]`) is written.
6. You did not enter real personal information, customer material, or confidential information anywhere.

## 7. Troubleshooting

| Symptom | Cause | How to fix |
|---|---|---|
| Verification takes too long | The checklist has too many items, or the AI result is too long | Keep only the required items (numbers, dates, people, sources, omissions) and move the rest to a low-severity check. Fix the work instructions to shorten the output |
| You miss errors every time | You compared in only one direction | Keep the two-way comparison, and go item by item (numbers → dates → people → sources), looking at only one kind at a time |
| The result is different every time you re-run | AI responses can differ even for the same request | Change only one thing at a time and record it. Set a limit of 2 times, and after the limit, a person writes it directly |
| The same error appears even after re-running | The work instructions do not have that rule, or it is vague | Add specific prohibitions and exception handling to the work instructions (CH10) and put it into the test cases |
| You suspect the source text is wrong | An error in the source material itself | Check with the person who wrote the source text. Until you check, leave it as "Needs confirmation" |
| There is no approver | The owner of the approval point has not been decided | Find out your organization's approver (CH11). Do not share until it is decided |
| Personal information showed up during verification | It was mixed into the input material | Stop using it, tell the owner, and delete that conversation (CH03 section 7) |
