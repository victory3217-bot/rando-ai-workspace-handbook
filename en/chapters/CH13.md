## 1. Learning Objectives

When you finish this chapter, you will be able to:

- Explain the differences among storage, sync, backup, and version history.
- Tell an original from a copy, and manage file versions with file names and a change log table.
- Know the order of steps for recovering a file that was edited by mistake or deleted.
- Explain that cloud trash and version history exist, and that they are not a substitute for backup.
- Create a backup plan and a recovery checklist for the candidate A work folder.
- Decide the change management procedure to follow when you change work materials and work instructions.

## 2. Core Concepts

**Terms used in this chapter**
- **Storage**: keeping a file somewhere.
- **Sync (synchronization)**: a feature that makes the other side match when you change one side (CH05).
- **Backup**: a copy you keep *separately* in case of an accident.
- **Version**: a number that tells apart each edit of the same file (`v01`, `v02`).
- **Change log**: a record of when, who, what, and why something was changed.
- **Recovery**: bringing back a file that was deleted or changed by mistake. A **restore test** checks that a backup can actually be brought back.
- **Trash · version history**: deleted files · earlier states that a service keeps for a set period. Conditions differ by service.

### 2-1. The difference among storage, sync, and backup

| | Storage | Sync | Backup | Version history |
|---|---|---|---|---|
| What it does | Keeps the file | Makes several places match | Keeps a separate copy | Keeps earlier states |
| If you delete | It is gone | It may be gone from the other places too | The backup copy remains | Can be restored, depending on the service's conditions |
| If you edit by mistake | Stays as is | The other places may change too | The earlier copy remains | You may be able to go back to an earlier version |
| Who is responsible | You | Service settings | You (plan and tests) | The service's conditions |

> **Official documentation check — sync and deletion, checked on 2026-10-26**
>
> - When you use Google Drive for desktop, edits you make to a file are automatically synced to both your computer and Google Drive. `[S11]`
> - When files are mirrored or streamed in Drive for desktop, a file you put in the trash goes to the trash *everywhere*. `[S14]`
> - Even after you move a file to the trash, people you shared it with can still access it until it is permanently deleted, and files in the trash use up storage space until they are permanently deleted. `[S14]`

> **Author's interpretation** As the facts above show, sync *also spreads deletions.* That is why **sync is not backup.** Do not feel safe just because a file is in the cloud; keep a separate copy in a place that is not synced (section 2-7).

### 2-2. Telling originals from copies

This restates the CH04 principle. Decide on *one place* for the original (the "location of the original" in CH05), and mark everything else as a copy. A backup copy is a copy, and **you do not edit it.** If you start editing a backup copy, it is no longer a backup but just another working file.

### 2-3. File version management

There are two main ways to manage versions. For non-programmers, this book **uses the first method as the default.**

| Method | Description | Advantage | Caution |
|---|---|---|---|
| ① Version number in the file name | Save as `v01`, `v02` | Visible, and needs no tool | Useless if you do not raise the number. The number of files grows |
| ② The service's version history | The cloud keeps earlier states | Automatic | Conditions and periods differ by service |

> **Official documentation check — the service's version history, checked on 2026-10-26**
>
> - In Google Drive, version history for Google Docs, Sheets, and Slides is different from the version history of other files such as PDFs and images. `[S15]`
> - In Google Drive, for older versions of a past document only the most recent one is stored, and if you select `Keep forever`, it is kept indefinitely. `[S15]`
> - In Google Drive, you can check changes in Activity to see who edited, moved, and shared a file. `[S15]`
> - In OneDrive, Microsoft 365 subscribers are said to be able to restore earlier versions of a file or restore their whole OneDrive to a point within the last 30 days. `[S13]`

This book has not verified the *detailed conditions* of version history (number of versions kept, period). Check them yourself in your own account before relying on them.

### 2-4. Managing file names and change logs

The file naming rule is the CH04 rule `[date]_[task]_[content]_[version]`. On top of that, keep a *change log table for each document*. It is especially needed for work instructions (the revision log in section 8 of CH10) and knowledge documents (CH08).

```text
Change log table
Document name / number:
Version | Date | Changed by | What changed | Why it changed | Check (test / verification) | Where the previous version is kept
v01 | 2026-10-26 | Me | First draft | | CH10 test | 
v02 | 2026-10-26 | Me | Added the phrase "Needs confirmation" to the output format | Test T2 failed | Passed after test re-run | 90_Archive
```

Principles: change one thing at a time, write down why you changed it and the check result, and do not delete the previous version; keep it in `90_Archive` (CH10).

### 2-5. Recovering a file edited by mistake

**Order of steps (the author's suggestion):**
1. **Stop.** Do not save any more (to avoid overwriting) and close the file.
2. **Look in nearby places first:** the earlier version file you saved (`v01`) → the trash → the service's version history → the backup.
3. **Open the recovered copy under a *new name*.** Do not overwrite the original name right away; check the content first, then replace.
4. **Record it:** write what went wrong and why in the change log table and the error log (CH12).

The Windows Recycle Bin is where files you delete on your own computer go temporarily. After you empty the Recycle Bin, you often cannot restore the files.

### 2-6. Cloud trash and version history

> **Official documentation check — cloud trash, checked on 2026-10-26**
>
> - In Google Drive, a file you move to the trash is permanently deleted after 30 days, and if you select `Empty trash`, it is permanently deleted immediately. `[S14]`
> - In Google Drive, if the file owner permanently deletes a file, the people it was shared with lose access too. `[S14]`
> - In OneDrive, files you deleted or overwrote can sometimes be restored: within 30 days of deletion for personal accounts, and within 93 days for work or school accounts (unless an administrator changed it). After you permanently delete a file from the recycle bin it cannot be restored, and files that someone else shared with you cannot be restored. `[S13]`

> **Author's interpretation** Trash and version history are a **convenient safety net**, but they have *periods and conditions*, so they cannot replace backup. If you emptied the trash or the period has passed, the service cannot bring the file back. The official documents this book read cover Google Drive deletion and some of its version history, and OneDrive deletion restore; this book has not verified every recovery feature of the two services.

### 2-7. Safe backup rules

> **Author's interpretation** The rules below are teaching rules. If your organization has backup or retention rules, they take priority.
>
> 1. **Two or more copies, in different places:** keep one more copy on *a different device or a different service* from where the original is. A different folder on the same computer is lost together with it if the computer fails.
> 2. **A place that is not synced:** keep the backup somewhere that is not a sync target (for example, an external storage device, or a separate storage place your organization allows). A copy kept in a synced folder may have deletions spread to it too (`[S14]`).
> 3. **On a regular schedule:** set *a schedule you can keep*, such as when a task ends or once a week (the author's suggestion, not tested).
> 4. **Restore test:** you only know a backup works by *bringing it back*. Restore a fictional file once.
> 5. **Respect the tiers (CH03):** for tier C material, beyond not uploading it to AI services, *also check your organization's rules on where to back it up*. Do not back up company material to a personal cloud or a personal device.
> 6. **Write down dates:** record the date of the last backup and the date of the last restore test.

### 2-8. Change management for work materials and work instructions

Work instructions (CH10) and knowledge documents (CH08) change how AI behaves and what it produces, so they need a *procedure for changing them*.

```text
Find a needed change (error log CH12, test CH10) → write the reason and where to change → change one thing at a time (new version)
  → check with test cases (CH10) → if it passes, approve it and move the previous version to 90_Archive → record it in the change log table
  → replace the instructions and knowledge files you put in the AI project with the same version (CH06·CH07) → update the status and update date in the knowledge index (CH08)
```

- If the document and the AI project's instructions are *different versions*, the rules people read and the rules AI follows will differ.
- If a knowledge document is retired, change its status in the index to `retired` and remove it from the AI project too (CH08).
- You must be able to recover the earlier version of the work instructions. That is why the earlier version is kept in `90_Archive`.

**About Git:** Git is a program that manages the change history of files in detail, and developers use it a lot. This book's core course does not require it; file-name versions and the change log table are enough. Git and GitHub are covered in an optional course (Git and GitHub basics).

## 7. Troubleshooting

| Symptom | Cause | How to fix it |
|---|---|---|
| I made a backup but cannot restore it | You did not run a restore test, the file is corrupted, or you edited the backup copy | Put a restore test in the schedule and do not edit backup copies. Check whether an earlier backup exists |
| I backed up to a synced folder and it was deleted too | Sync also spreads deletions `[S14]` | Back up to a place that is not synced. Check the service's trash `[S14]` `[S13]` |
| I emptied the trash but I need the file | Permanent deletion `[S14]` `[S13]` | The service cannot bring it back, so look for a backup or an earlier version file. From now on, check before emptying |
| I overwrote without raising the version number | You did not follow the rule | Look in the service's version history (check conditions) or the backup, and add "raise it before sharing" to the rules |
| I do not know which file is the latest | Copies exist in several places | Decide on one location for the original (CH05) and mark the rest as copies. Look at the change log table |
| I changed the work instructions but AI still behaves the old way | You did not change the AI project's instructions | Replace the project instructions and knowledge files in CH06·CH07 with the same version |
| I do not know where to back up company material | You did not check the rules | Ask the person in charge which places are allowed, and until it is confirmed, leave the place in the backup plan as "Needs confirmation" |
| I backed up company material to a personal cloud | You did it before checking the rules | Do not hide it; tell the person in charge and delete it (section 7 of CH03) |
