## 1. Learning Objectives

When you finish this chapter, you will be able to do the following.

- Explain the difference between a one-time prompt and reusable work instructions.
- Write the eight elements of work instructions (purpose and scope, input conditions, execution steps, output format, prohibitions, exception handling, verification criteria, revision and version log).
- Write the work instructions for candidate A in Notepad or Markdown.
- Test the work instructions on fictional cases and record the results.
- Organize the problems found in testing into an improvement list and create a new version of the work instructions.

## 2. Core Concepts

**Terms used in this chapter**
- **Work instructions**: A document that states what rules and order a task follows. It is both an instruction you give AI and a work manual that people read and check. The *project instructions* in CH06 and CH07 are one form of work instructions.
- **Scope**: The boundary between what these work instructions cover and what they do not.
- **Exception handling**: What to do when things are not normal (for example, material is missing).
- **Verification criteria**: The standard for judging whether a result is correct.
- **Version**: A number that tells apart each revision of the work instructions (`v01`, `v02`).
- **Test**: Checking whether the work instructions work properly by using set cases.

### 2-1. One-time prompts and reusable work instructions

| | One-time prompt | Work instructions |
|---|---|---|
| Use | Used once and forgotten | Used repeatedly |
| Content | One line of request | Purpose, scope, input conditions, steps, format, prohibitions, exceptions, verification |
| Who knows it | The person who wrote it | Me, coworkers, the AI service |
| How to fix it | Case by case | Raise the version and record the reason |
| Verification | None | Has criteria and test records |

> **Author's interpretation** Work instructions are not *magic that makes AI do well on its own*. AI can break them even while following them. The value of work instructions lies in **stating in writing what I expect from AI, and having a standard for noticing and fixing it when AI breaks them**. This book has not verified that writing work instructions improves results.

### 2-2. The eight elements of work instructions

```text
# Work instructions: [task name]
- Document number / version / updated on / author / tier

 ## 1. Purpose and scope
 ## 2. Input conditions
 ## 3. Execution steps
 ## 4. Output format
 ## 5. Prohibitions
 ## 6. Exception handling
 ## 7. Verification criteria
 ## 8. Revision log
```

### 2-3. Purpose and scope

- **Purpose:** Take the `purpose of working with AI` from CH01 as it is and write it in one sentence.
- **Scope:** Write *what you do* and *what you do not do* side by side. Writing down what you do not do keeps the work instructions from growing and keeps AI from overstepping.

### 2-4. Input conditions

Write which material you accept (name, format, tier) and *which material you must not accept*. Example: "Accept only masked meeting notes (tier B). Do not accept material that still has names or contact details; report it instead." If the input material is in your knowledge base (CH08), write its document number.

### 2-5. Execution steps

Write them with numbers, *one action at a time, in order*. Each step should be one action. For a step that needs a judgment, write the criterion for the judgment next to it. These steps develop into a workflow diagram and run procedure in CH11.

### 2-6. Output format

Write the table columns, required items, length, and marking rules (for example, mark unknown items as "Needs confirmation"). The "condition for saying it is done" from CH09 goes here.

### 2-7. Prohibitions and exception handling

- **Prohibitions:** Writing content that is not in the notes, changing names, amounts, or dates, making decisions on someone's behalf, sending anything outside, handling personal information or passwords, and so on.
- **Exception handling:** Write "in this situation, do this" as a table.

| Situation | What to do |
|---|---|
| There is no owner or deadline | Mark it "Needs confirmation" and collect it in a list |
| Personal information appears in the input material | Do not process it; tell a person |
| Rules conflict or an unknown term appears | Do not guess; ask a person |

### 2-8. Verification criteria, and revision and version management

**Verification criteria:** Write how you will check the result (the fact-check table and number recalculation from CH09) and the **pass/fail conditions**. Example: "Every sentence in the table can be found in the notes. Content not in the notes: 0 items."

**Revision and version management (the author's suggestion):**
- Put the version in the file name (`MeetingMinutes_Instructions_v01.md`, CH04).
- Make revisions *one at a time*, and write the reason and date in the `Revision log`.
- Finalize the new version only after you confirm that test results have improved. Before finalizing, keep the previous version in `90_Archive`.
- When you change the work instructions, change the instructions you put into your AI project (CH06, CH07) to the same content. If you do not, the document and the rules the AI follows will differ.
- More detail on backup and version management is covered in CH13 according to the table of contents.

### 2-9. Instruction document structure of a public harness (supporting example)

> **Harness case — Instruction documents of a public harness that separate role, procedure, and rules**
>
> - Repository: rando-promotion-harness
> - File path: `agents/promotion-agent.md`, `core/PLAYBOOK.md`
> - What was confirmed: `agents/promotion-agent.md` separates the role (creating drafts and verifying facts, while final confirmation and the decision to publish belong to the user), an 8-step run procedure (confirming the target, reading tone preferences, judging the channel, judging missing information, asking questions in a batch, writing the draft, fact verification, output), and "things to keep." `core/PLAYBOOK.md` keeps common rules in one place and describes input principles (use only facts the user stated, and do not guess and fill in things such as prices the user did not state), absolute rules (do not put personal information into prompts, and so on), and handling principles for missing information (ask a question, or leave `[확인필요]` (Korean for "needs confirmation")). These documents are for creating promotional copy and differ from this book's meeting minutes task.
> - Status: Public repository. On 2026-10-26 we confirmed that commit `3725763` is the same as the latest remote commit. The `output/` folder in the local copy is not on the remote, so it was not used as evidence.
> - Verified on: 2026-10-26

> **Author's interpretation** What to take from this case is not the folder structure or the code but *the idea of dividing documents*. (1) Write the role (what this person or agent is in charge of) and the run procedure (in what order). (2) Gather the rules (what not to do) in one place. (3) Set an input principle: "do not fill in what was not said; if you do not know, ask or mark it." In this chapter, you combine these into one page of work instructions. This case only shows what work instructions can look like; it is not evidence that writing such work instructions improves results.

## 3. Workplace Application

At the fictional company Example Trading Co., Gasang Han saw in CH09 that the AI's drafts went wrong in a similar way every time, and moved the rules that block those error types into the work instructions. (All fictional)

| Error found in CH09 | Where it went in the work instructions |
|---|---|
| Fabricated a quotation that is not in the notes | Prohibitions: "Quotations in quotation marks only from words in the notes" |
| Changed "revision proposal" to "reduction proposal" | Prohibitions: "Do not change key words" |
| Filled in a name for an item with no owner | Exception handling: "If it is empty, 'Needs confirmation'" |
| Left out an open item | Verification criteria: "Compare the number of undecided items in the source with the number of open items in the result" |

Gasang Han tested the instructions with three fictional notes, wrote down what to improve, and created `v02`. The effect (whether time went down or errors went down) was not confirmed by this book; it is a fictional expectation.

## 6. Verify the Result

You are done when all of the following are true.

1. The work instructions have all 8 elements, and both what you do and *what you do not do* are written.
2. The input conditions include material you do not accept and what to do then, and the tier (CH03) is connected.
3. The execution steps are written in numbered order, one action per step.
4. At least two of the error types found in CH09 are reflected in the prohibitions and exception handling.
5. The verification criteria include what a person checks and the pass condition.
6. The test record has the expected behavior, actual result, and pass/fail for the three cases, and the vague sentences are written down.
7. There is an improvement list, and the `v02` revision log has the reason for the change and the test result.
8. The work instructions and the test material contain no real personal information, customer material, or confidential information.

> **Author's interpretation** A fictional example of test results (the author's example, not a correct answer; the case where a person did the work as a substitute)
>
> ```text
> T2 | Expected: deadline and owner as "Needs confirmation" (work instructions, 6. Exception handling) | Wrote "Staff C" as the owner of agenda 2 → fail
>     | Problem sentence: The phrase "If no owner is decided, Needs confirmation" is only in section 6 and not in section 4, Output format, so it is easy to miss
> Improvement 1 | Add the same phrase to the output format as well / priority high / v02
> ```

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| The work instructions became too long | The scope grew or there are too many rules | Narrow the scope with what you do not do, and split the task in two. Move rules into a knowledge document (CH08) and refer to them by number |
| AI does not follow part of the work instructions | The rules are vague or conflict with each other | Write one rule per sentence and remove conflicts. Add a case where AI broke the work instructions to your test cases |
| Test results differ every time | AI's responses can differ even for the same request | Run each case several times, and write pass criteria as conditions you can check, not as loose sentences |
| I fixed the work instructions, but AI still does it the old way | You did not change the instructions in the AI project | Change the project instructions in CH06 and CH07 to the same version and test |
| I cannot tell which version is the latest | You did not follow the file naming rule | Check the `v` number in the file name and the revision log, and move previous versions to `90_Archive` |
| Making it like the public harness is hard | The case is a folder structure for developers | Take only "write role, procedure, and rules separately," not the folder structure. One page is enough |
| Personal information got mixed in during testing | You used material that was not fictional | Stop using it, tell the person in charge, and delete that conversation (CH03 section 7) |
